PRD: Personal AI Assistant — "Zyra"

Repo: github.com/Asifkarim683 — suggested repo name: zyra-assistant

1. Overview

A personal, voice/text-interactive AI assistant that responds to commands, automates routines (e.g., morning music + greeting), and eventually ships as a mobile app. Zyra: a proactive, conversational assistant integrated into daily life — voice/text commands, scheduled routines, and (later) a mobile app. Built hybrid: deterministic routines run locally with no LLM call; open-ended conversation goes through an LLM (local or Claude API).

2. Goals

  • Let Eren interact with the assistant via voice or text and get fast, useful responses.
  • Automate scheduled actions (alarms, music, greetings) without manual triggering, and without depending on network/LLM availability.
  • Build toward a mobile app once the core engine is stable.
  • Treat security (auth, data storage, permissions, command execution) as a first-class requirement.
  • Keep the system efficient: route simple commands directly to skills, reserve LLM calls for things that actually need reasoning.

3. Non-Goals (v1)

  • Full smart-home control (lights, thermostats) — future phase.
  • Multi-user support — single-user assistant for now.
  • Fully offline v1 — offline is a supported mode, not the only mode (see Section 8).

4. Target Platforms

Phase Platform Notes
Phase 1 Desktop/local app or web dashboard Core brain + voice/text interface
Phase 2 Mobile app (Android first, given dev background) Wraps same backend via API

5. Core Features

5.1 Intent Router (new — do this first)

Before anything hits the LLM, a lightweight router pattern-matches the input:

  • Matches a known command ("play music", "set alarm", "what time is it") → dispatch directly to the skill, no LLM call. Fast, cheap, and works even if the LLM/network is down.
  • No match → forward to the LLM reasoning layer for open-ended conversation/intent parsing. This is the single biggest efficiency win: most personal-assistant traffic is simple commands, not open-ended chat.

5.2 Conversational Interface

  • Accepts voice input (speech-to-text) and/or typed text.
  • Unmatched input goes to an LLM (Claude API, or a local model — see Section 8) for reasoning + response generation.
  • Text-to-speech reads responses back aloud.
  • Maintains short-term conversation context (last N turns) for follow-ups.
  • Streaming + barge-in: stream TTS output token-by-token rather than waiting for the full response; detect the wake word mid-playback so Eren can interrupt and redirect instead of waiting it out.

5.3 Scheduled Routines

  • Cron-like scheduler (node-cron, or OS-level scheduled task) triggers actions at set times.
  • Example: 7:00 AM weekday alarm → play music playlist → TTS says "Good morning, Eren" (Zyra's voice).
  • Schedules configurable (add/edit/delete times, playlists, messages) via command or config file.
  • Routines call skills directly (bypass the LLM entirely) — deterministic and reliable.

5.4 Music Playback

  • Integrates with a music source: local files, or a service API (Spotify Web API is the practical choice given OAuth + playback control support).
  • Commands like "play something upbeat" map to playlist/genre selection.

5.5 Skill System (modular)

  • Each skill (music, alarms, weather, reminders, web search, later: vision, memory-lookup) is a self-contained handler the router dispatches to.
  • New skills plug in without touching core routing logic.
  • Command validation/allowlisting: skills that execute system-level actions validate and allowlist inputs — no arbitrary shell execution from parsed LLM output. Reject dangerous constructs outright rather than trying to sanitize them.

5.6 Memory (Phase 2+)

  • Short-term: rolling conversation context (in-memory or session table).
  • Long-term: lightweight vector store (e.g., a local embeddings DB) for preferences and past interactions, so the assistant improves with use rather than starting fresh every session.

5.7 Vision Skill (future)

  • Optional local vision model skill ("what's on my screen") — same skill-dispatch pattern as everything else, just another modular handler.

5.8 Mobile App (Phase 3)

  • Thin client that talks to the backend over authenticated API calls.
  • Push notifications for reminders/alarms.
  • Voice input via device mic.
  • Device-level auth (PIN/biometric) before the app can issue commands.

6. Security Requirements

  • Authentication: Backend API requires a token (JWT or API key) for every request; no open endpoints.
  • Secrets management: API keys (LLM provider, Spotify, etc.) stored in environment variables / a secrets manager — never hardcoded or committed to Git.
  • Least privilege on integrations: OAuth scopes limited to only what's needed (e.g., playback control, not full account access).
  • Local data encryption: Conversation logs, schedules, and personal data encrypted at rest.
  • Network security: HTTPS only for any API the mobile app or web client talks to.
  • Command allowlisting: system-executing skills validate/allowlist parsed intents before execution (see 5.5) — this is the pattern to build in from day one, not retrofit later.
  • Low-power/idle mode: when idle, unload the LLM from memory and shorten model residency, keeping only wake-word detection active — reduces attack surface and resource use simultaneously.
  • Access control for mobile app: device-level auth before the app can issue commands.
  • Audit trail: log executed commands (not raw sensitive content) so you can review what the assistant did and when.

7. High-Level Architecture

[Voice/Text Input] → [STT (if voice)] → [Intent Router]
                                            ↓
                         matched? ──yes──→ [Skill Dispatcher] → [Music] [Alarm] [Other Skills]
                                            ↓ no
                          [LLM Reasoning Layer (Claude API / local)]
                                            ↓
                                    [Skill Dispatcher] (if action needed)
                                            ↓
                                    [TTS Output / App UI]

[Scheduler] → triggers Skill Dispatcher directly, bypassing router + LLM entirely

8. Offline Mode

Fully offline is achievable — several open-source "Jarvis" clones already prove this pattern out:

Component Cloud (default) Offline alternative
Reasoning Claude API Ollama + small quantized model (qwen2.5:3b/7b, llama3.2)
Speech-to-text Cloud STT Whisper / whisper.cpp (runs locally, CPU is fine)
Text-to-speech Cloud TTS Piper (local, natural-sounding)
Wake word n/a Porcupine or openWakeWord (always local)

Recommended approach: build the skill/routine layer to be offline-capable by default (it never needed the LLM anyway), and make the LLM backend swappable — Claude API when online for best quality, Ollama fallback when offline or for privacy-sensitive queries. A config flag (LLM_MODE=cloud|local) is enough to start.

9. Tech Stack Recommendation (given your background)

  • Backend: Laravel or Spring Boot (you already know both).
  • Frontend/dashboard: React.
  • LLM: Claude API (cloud) + Ollama (offline fallback).
  • STT/TTS: Whisper/whisper.cpp + Piper for offline; Web Speech API for quick prototyping.
  • Mobile: React Native, to reuse JS/React knowledge.
  • Database: MySQL for structured data; a lightweight local vector store for long-term memory.
